---
title: Connect Gitea
description: Verify repository access, configure webhooks, and import existing issues.
---

Connect a Kaneo project to one Gitea repository to sync issues and respond to branch and pull-request activity. You need permission to manage the Kaneo project, a Gitea token that can read the account and repository and write issues, and repository admin access to create its webhook.

## Connect the repository

1. Create a personal access token in Gitea under **Settings → Applications**. Give it the scopes needed to read your user and repository and write issues. The token’s account must also have write access to the target repository.
2. In Kaneo, open **Settings → Projects**, select your project, and open **Integrations → Gitea**.
3. Enter the Gitea base URL, such as `https://git.example.com`. Use the final URL directly, without `/api/v1`, credentials, a query string, or a fragment.
4. Enter the access token and repository owner and name. You can also browse repositories from the form.
5. Choose **Verify access** and resolve any reported problem, then save the connection.

The API must be able to reach your Gitea server. Verification checks the token and repository permissions; it does not prove that webhooks can reach Kaneo in the other direction.

## Configure the webhook

After saving, Kaneo shows a webhook URL and secret. Copy both into a repository webhook in Gitea under **Settings → Webhooks → Add Webhook → Gitea**.

| Gitea setting | Value |
| --- | --- |
| Target URL | The webhook URL shown in Kaneo |
| HTTP method | POST |
| Content type | `application/json` |
| Secret | The exact secret shown in Kaneo |
| Active | Enabled |

Select push, pull request, issue, and issue comment events. Include issue label events if your Gitea version exposes that selection. Kaneo handles `issue_label`; the Git branch/tag **Create** event is not a label event.

The URL has this shape:

```text
https://kaneo.example.com/api/gitea-integration/webhook/INTEGRATION_ID
```

Use Gitea’s test delivery, then create a test issue and confirm it appears in Kaneo. A successful test response proves the request arrived; checking the resulting task proves issue sync works. See [Gitea’s webhook documentation](https://docs.gitea.com/usage/repository/webhooks/) for its settings and delivery log.

## Import existing issues

Save the repository connection, verify its current settings, then choose **Import Issues**. Verification is cleared when you reload the page or change connection details. If import is disabled, verify again. When replacing the token, save it before importing because the importer uses the saved connection.

## Configure automation

Choose your branch naming pattern in the integration settings. In the project’s [Workflow settings](/core/functional/configure-workflows), map branch pushes, opened pull requests, and merged pull requests to the intended columns. Try one task first and check its status before adopting the pattern across your team.

## Replace a token or disconnect

To rotate credentials, enter a replacement token, verify access, and save. On an existing connection, an empty token field keeps the saved token; it does not clear it.

Choose **Disconnect** to remove the Kaneo connection. This does not delete the Gitea repository or Kaneo tasks. Remove the webhook in Gitea as well, and revoke its token if nothing else uses it.

## Troubleshooting

| Problem | What to check |
| --- | --- |
| URL redirects or returns HTML | Use Gitea’s final base URL and make sure an authentication proxy is not intercepting API requests. |
| Repository not found | Check owner, name, and token access to private repositories. |
| Verification succeeds, writes fail | Check token scopes as well as the account’s repository permissions. |
| Invalid webhook signature | Copy the current secret from Kaneo and save it in Gitea. |
| No tasks arrive | Check recent Gitea deliveries, selected events, repository identity, and the active connection. |
| Task does not move after a push | Check the branch naming pattern and workflow mapping. |
