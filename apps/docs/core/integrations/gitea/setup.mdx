---
title: Connect Gitea
description: Verify repository access, configure webhooks, and import existing issues.
---

Connect a Kaneo project to one Gitea repository to sync issues and respond to branch and pull-request activity. You need permission to manage the Kaneo project, a Gitea token that can read the account and repository, and repository admin access to create its webhook. Two-way issue sync also requires permission to write issues.

## Connect the repository

1. Create a personal access token in Gitea under **Settings → Applications**. Give it the scopes needed to read your user and repository. For **Two-way sync**, also grant issue write access; the token’s account must have write access to the target repository. **Ingest only** and **Off** do not require issue write access.
2. In Kaneo, open **Settings → Projects**, select your project, and open **Integrations → Gitea**.
3. Enter the Gitea base URL, such as `https://git.example.com`. Use the final URL directly, without `/api/v1`, credentials, a query string, or a fragment.
4. Enter the access token and repository owner and name. You can also browse repositories from the form.
5. Choose the **Issue sync mode** before connecting, then choose **Verify** and resolve any reported problem. Save the connection with **Connect**.

The API must be able to reach your Gitea server. Verification checks the token and repository permissions; it does not prove that webhooks can reach Kaneo in the other direction.

## Choose an issue sync mode

| Mode | Behavior |
| --- | --- |
| **Two-way sync** (`sync`) | Sync issues, comments, and labels in both directions. This is the default, including for connections created before this setting was added. |
| **Ingest only** (`ingest-only`) | Read Gitea issues, comments, and labels into Kaneo. Kaneo does not create or update Gitea issues, comments, or labels, including task-link comments and status labels. |
| **Off** (`off`) | Ignore inbound issue, issue-comment, and issue-label events and stop outbound issue, comment, and label changes. Manual issue and pull-request import is also disabled. |

On an existing connection, selecting a mode submits the change immediately. Changing the mode keeps existing Kaneo tasks, Gitea issues, and their links. It does not export existing tasks or automatically catch up on events missed in another mode. Rotating credentials or saving connection details preserves the selected mode.

Switching to **Two-way sync** checks the saved connection's repository write permissions before saving; a failed check leaves the mode unchanged. The token must also have the required issue-write scopes. If the connection changes while verification is running, reload the settings and try again.

Switching away from **Two-way sync** cancels queued outbound issue repairs. **Ingest only** still processes queued inbound Gitea updates; **Off** discards them. Saving an unchanged mode does not rewrite queued work.

A mode change waits for admitted outbound requests to finish or time out before saving. Once **Ingest only** or **Off** is saved, stale work cannot start new outbound issue, comment, or label requests while that mode remains active. Requests already received by Gitea may still complete remotely after a timeout; they cannot be cancelled by a later mode change.

All three modes retain live branch, push, and pull-request linking and workflow automation while the connection is active. **Off** is not a connection-wide disable switch. Task-link comments are available only in **Two-way sync**; their saved preference is kept in the other modes.

## Configure the webhook

After saving, Kaneo shows a webhook URL and secret. Copy both into a repository webhook in Gitea under **Settings → Webhooks → Add Webhook → Gitea**.

| Gitea setting | Value |
| --- | --- |
| Target URL | The webhook URL shown in Kaneo |
| HTTP method | POST |
| Content type | `application/json` |
| Secret | The exact secret shown in Kaneo |
| Active | Enabled |

Select push, pull request, issue, and issue comment events. Include issue label events if your Gitea version exposes that selection. Kaneo handles `issue_label`; the Git branch/tag **Create** event is not a label event.

The URL has this shape:

```text
https://kaneo.example.com/api/gitea-integration/webhook/INTEGRATION_ID
```

Use Gitea’s test delivery to check that requests reach Kaneo. In **Two-way sync** or **Ingest only**, create a test issue and confirm it appears in Kaneo. In **Off**, issue events are intentionally ignored; exercise a branch push or pull request tied to a Kaneo task instead. A successful test response proves the request arrived; checking the resulting task proves the selected automation works. See [Gitea’s webhook documentation](https://docs.gitea.com/usage/repository/webhooks/) for its settings and delivery log.

## Import existing issues

In **Two-way sync** or **Ingest only**, save the repository connection, verify its current settings, then choose **Import issues**. Verification is cleared when you reload the page or change connection details or issue sync mode. If import is disabled, verify again. When replacing the token, save it before importing because the importer uses the saved connection. **Off** disables this combined issue and pull-request import without cutting off live pull-request webhooks.

## Configure automation

Choose your branch naming pattern in the integration settings. In the project’s [Workflow settings](/core/functional/configure-workflows), map branch pushes, opened pull requests, and merged pull requests to the intended columns. Try one task first and check its status before adopting the pattern across your team.

## Link task IDs to Kaneo

Every task has a short link built from its workspace and ticket ID, such as `https://kaneo.example.com/acme/task/KAN-12/fix-login-timeout`. The title at the end is optional and ignored, so `https://kaneo.example.com/acme/task/KAN-12` opens the same task. **Copy link** on a task gives you this link, which shows your workspace’s part of the path.

To turn references such as `KAN-12` in Gitea commits and pull requests into links, open the repository’s **Settings**, enable **Use External Issue Tracker**, and set:

| Gitea setting | Value |
| --- | --- |
| External Issue Tracker URL | `https://kaneo.example.com` |
| External Issue Tracker URL Format | `https://kaneo.example.com/acme/task/{index}`, with your workspace in place of `acme` |
| External Issue Tracker Number Format | Alphanumeric |

The alphanumeric format only matches keys of one to ten uppercase letters. For any other key, choose **Regular Expression** and match your project’s key exactly, such as `(DE_-\d+)`, `(ПРО-\d+)`, or `(OPS\.2-\d+)` with the `.` escaped. To link several projects, list their keys: `((?:KAN|OPS)-\d+)`.

## Replace a token or disconnect

To rotate credentials, enter a replacement token, verify access, and save. On an existing connection, an empty token field keeps the saved token; it does not clear it.

Choose **Disconnect** to remove the Kaneo connection. This does not delete the Gitea repository or Kaneo tasks. Remove the webhook in Gitea as well, and revoke its token if nothing else uses it.

## Troubleshooting

| Problem | What to check |
| --- | --- |
| URL redirects or returns HTML | Use Gitea’s final base URL and make sure an authentication proxy is not intercepting API requests. |
| Repository not found | Check owner, name, and token access to private repositories. |
| Verification succeeds, writes fail | Check token scopes as well as the account’s repository permissions. |
| Invalid webhook signature | Copy the current secret from Kaneo and save it in Gitea. |
| No tasks arrive | Check recent Gitea deliveries, selected events, repository identity, the active connection, and whether issue sync is set to **Off**. |
| Task does not move after a push | Check the branch naming pattern and workflow mapping. |
